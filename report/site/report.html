CS3263 · AI Assistant for Software Engineering · results as of 15 Oct 2026

Can an LLM tell whether C code is safe, and does handing the question to Z3 help?

We gave small open-weight models 120 C functions and asked whether any input allowed by the caller's preconditions can cause an out-of-bounds access, a division by zero, a signed overflow or an invalid shift. Each model answered in two ways: directly, and by writing a Z3 script that the solver decides. Every bug a model claimed was re-run on the real code under clang's sanitizers.

Key findings

  • 56%qwen direct accuracy

    Direct review is a coin flip with a "safe" bias. Direct answers score 56% (qwen) and 54% (llama), and the scores are the same on two-line arithmetic as on nested loops. qwen gives both versions of a minimal pair the same verdict in 85% of pairs and calls both "safe" in 44 of 60. It catches 25% of real bugs. Chain of thought does not change this.

  • 67.5%qwen LLM→Z3 on flat code

    Translation reasons when it runs. On flat arithmetic, qwen's Z3 scripts are the most accurate LLM approach (vs 57.5% direct). On the instances where its script executed, Z3 scores 66.7% (direct review scores 58% on the same instances). It also gets both precondition twins right four times as often as direct review.

  • 60%qwen scripts that executed

    But writing the script is the bottleneck. The models invent APIs (BVSDivNoUnderflow, from z3.solvers import …), use Python's | on Z3 conditions, and fall into repetition loops. llama's bare scripts executed 0% of the time. Accuracy collapses on loops (19%) and helper functions (6%).

  • 23%qwen Z3 with guidance

    More tool knowledge made it worse; repair barely helped. A C-to-Z3 cheat-sheet dropped qwen from 40% to 23%: more invented helper names and more runaway outputs. Three rounds of error feedback added 5 instances. 83% of repair attempts repeated the previous script word for word.

  • 63%best LLM system (hybrid)

    Combining both is best, and replay makes bug reports trustworthy. Using Z3 when its script runs and chain of thought otherwise gives 63% accuracy and doubles recall (53% vs 25%). Re-running counterexamples on the real code filtered out every false alarm (precision 100%).

  • 100%CBMC, 1.7 s per function

    Classical tools win on this benchmark. CBMC and the gold Z3 encodings decide all 120 instances. Dictionary fuzzing finds 58 of 60 bugs. On small, self-contained C functions, the LLM's best job is to draft specifications for a sound tool, not to sign off on safety.

The study in brief

The question. Given a C function and the preconditions every caller guarantees, is there an allowed input that breaks one of four safety rules (bounds, division by zero, signed overflow, invalid shift)? If yes, the function is UNSAFE and the model should give that input.

flowchart LR
  I["C function + preconditions"] --> D["Direct: LLM says SAFE / UNSAFE + input"]
  I --> T["Translate: LLM writes a Z3 script"]
  T --> S["Sandbox runs Z3"]
  S -->|unsat| SAFE
  S -->|sat: model = input| W["Re-run input on real C code (ASan + UBSan)"]
  D -->|UNSAFE + input| W
  W --> C{"Sanitizer fires?"}
  C -->|yes| OK["Bug confirmed"]
  C -->|no| SP["Spurious claim"]

Benchmark: 120 functions, 60 minimal pairs

Four tiers: flat arithmetic (20 pairs), branches (19), loops (13), helpers and nested loops (8). Every UNSAFE function has a SAFE twin. In 37 pairs the twin fixes the code; in 23 the code is byte-identical and only the precondition differs. Every label is checked four ways: an executed witness, a reference Z3 encoding, CBMC, and fuzzing. All 120 pass.

Five ways to use the model

Direct: JSON answer only. Direct + CoT: structured step-by-step first. LLM→Z3: write a script under a fixed protocol. Guided: plus a C-vs-Z3 cheat-sheet and a worked example. Repair: plus up to 3 rounds of error and counterexample feedback, never the answer.

Executable is not the same as faithful.

  • False alarms: 15 of qwen's 42 bare SAT answers were on SAFE functions. For example, for the safe divisor slots | 1u it asserted slots == 0, modelling the bug it expected rather than the code it was given.
  • "Proofs of the wrong theorem": 9 UNSAT answers were on functions that do have bugs. Nothing in a pipeline without labels can flag these.
  • C's % was never translated: no script in any variant used SRem, so negative remainders were never modelled.

Reading the preconditions

In precondition twins the code is identical and only the caller's guarantee changes. For example, w * h is UNSAFE when the sides go up to 50,000 and SAFE when they go up to 46,340. A reviewer that ignores the precondition must get one of the two wrong.

The formal approach reads the preconditions; direct review mostly doesn't. The guidance was followed, and that made things worse. Having seen the eight real overflow helpers, qwen invented the missing combination BVSDivNoUnderflow 59 times. The error message listed the correct BVSDivNoOverflow in every one of those cases.

Repair: executable scripts rose from 40% to 49% after one round, then flattened (accuracy 23.3% → 27.5%, not significant). With greedy decoding, 210 of 253 repair attempts were identical to the previous script. We skipped llama's repair run: none of its guided first attempts executed, and the run would have taken about five hours.

What the models wrote

Chain of thought raises the right case, then dismisses it

return x / d; with precondition d != 0. The function is UNSAFE because of INT_MIN / -1.

"division by −1 can lead to overflow if x is INT_MIN. Specifically, INT_MIN / −1 results in INT_MAX, which is within the range of a 32-bit signed integer. Therefore, this operation does not violate the overflow invariant." Verdict: SAFE (qwen 7B, Direct + CoT)

bounds_violation = h < 0 | h >= size     # parsed as h < (0 | h) >= size → TypeError

Implementation

The full write-up is report/IMPLEMENTATION.md. It covers every decision and its rationale. Two generated appendices list every instance, precondition and reference Z3 encoding and every prompt, verbatim.

Safety rules (shown verbatim in every prompt)

Safety invariants (C semantics; `int` is 32-bit two's complement, `long long` is 64-bit):
  1. bounds   - every array/pointer access (read or write) uses an index i with 0 <= i < length of that array.
  2. div_zero - the right operand of every `/` and `%` is non-zero.
  3. overflow - no signed integer arithmetic overflows: +, -, *, unary -, and also
                INT_MIN / -1 and INT_MIN % -1. (Unsigned wraparound is well-defined and NOT a violation.)
  4. shift    - for `a << b` and `a >> b`: 0 <= b < bit-width of the (promoted) left operand;
                additionally for signed `a << b`: a >= 0 and the result must be representable.
The function is UNSAFE if there EXISTS an input satisfying all preconditions that makes the
function (including any function it calls) violate at least one invariant. Otherwise it is SAFE.

The Z3 protocol

The model declares one Z3 constant per parameter, named exactly like it. It creates s = Solver(), adds the preconditions, and adds one disjunction over every risky operation, each combined with the condition under which that operation runs. Then s is satisfiable exactly when the function is UNSAFE. The model may not call s.check(): we run the solver ourselves (30 s limit) and read the counterexample back by parameter name.

Checking answers

  • Sandbox: model-written scripts run in a separate python -I process with a scrubbed environment (no API keys), a throw-away directory, CPU, memory and time limits, and a macOS sandbox with no network and no writes outside the temp folder.
  • Replay: every claimed bug input is checked against the preconditions and run on the real C code, compiled with -fsanitize=address,undefined. A sanitizer report confirms it.
  • Labels: each is checked by an executed witness, the reference Z3 encoding (whose own counterexamples are replayed), CBMC with unwinding assertions, and 3,000 fuzz inputs. All 120 pass.

Models

qwen2.5-coder:7b and llama3.2:3b served locally by Ollama. Settings: temperature 0, seed 0, 8,192-token context (the guided prompt plus repair history needs it), at most 3,072 output tokens, one sample per instance. Every response is cached, so runs are resumable and exactly reproducible. Gemini 2.5 Flash and Flash-Lite are configured with thinking disabled.

Reference encodings worth knowing about

  • Euclid's GCD (T3-OVF-04-S) is proved safe with an inductive invariant instead of unrolling.
  • A sum of squares (T3-OVF-02) needed a lemma proved by a separate solver before the main query would finish.
  • One pair, the "is it safe to multiply?" check b <= INT_MAX / a, defeats both Z3 and CBMC. It is excluded and kept as a solver-limitations case study.

Responsible AI

  • Bug reports can be checked automatically; "safe" cannot. A replayed counterexample is evidence anyone can verify in seconds. An LLM's "looks safe" carries no artefact. An UNSAT from an LLM-written specification proves only the formula the model wrote, and "Z3: unsat" looks more authoritative than it is.
  • The dangerous error is false assurance. Both small models default to "safe" and miss 75–90% of bugs when asked directly.
  • Running model-written code is a security decision. Isolate it, and keep credentials out of its environment.
  • Recommended practice.
    • Act on confirmed counterexamples.
    • Show unconfirmed ones as hints.
    • Treat UNSAT as a prompt to review the generated specification (always display it).
    • Never present an LLM's "safe" as verification.
  • Disclosure. The benchmark instances and reference encodings were written with an AI assistant and accepted only after mechanical validation. The evaluated models come from other vendors.

Limits and next steps

  • Small, synthetic benchmark. 120 instances give about ±9-point intervals, and tiers are smaller still.
  • Small models only. One greedy sample per instance; results may change with scale.
  • llama's repair variant was not run. Its numbers are missing, not zero.
  • Next steps.
    • Gemini runs, once an API key is added.
    • Sampled or fresh-context repair.
    • Decoding restricted to the real Z3 API.
    • A faithfulness check for UNSAT answers.
