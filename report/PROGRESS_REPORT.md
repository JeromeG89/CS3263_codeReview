## 2. What the project does (proposal → implementation)

The proposal asks whether an LLM can tell if a function contains a mathematical safety violation, given the preconditions its callers guarantee. It compares two ways of using the LLM.

| | Proposal | What was built |
|---|---|---|
| Problem instances | "code snippets with predefined invariants" | 120 C functions plus caller preconditions. Four invariants: array **bounds**, **division by zero**, signed **overflow**, invalid **shift** |
| Approach 1 | LLM analyses the code directly | `direct` (answer immediately) and `direct_cot` (reason step by step first) |
| Approach 2 | LLM writes Z3 code; SAT = bug, UNSAT = safe | `z3` (bare instructions), `z3_guided` (plus a cheat-sheet of C-vs-Z3 pitfalls and one worked example), `z3_repair` (plus up to 3 rounds of error feedback) |
| Fallback plan | start with flat arithmetic, scale up | Tier 1 is flat arithmetic. Tiers 2–4 add branches, loops, and helper functions with nested loops, so the fallback point is built in |
| Discussion | advantages and limitations; Responsible AI | failure taxonomy of the generated Z3 code, significance tests, Responsible AI section drafted |

**Why C?** C makes these bugs concrete. Overflow, out-of-bounds access and division by zero are *undefined behaviour* in C, and clang's sanitizers (AddressSanitizer + UndefinedBehaviorSanitizer) detect each of them at runtime. That gives a ground-truth checker we can trust.

**Who wrote what.** You asked that the Z3 side and the data be produced with Claude, and the comparisons with Gemini or weaker models. Accordingly:
- Claude wrote the dataset and the reference ("gold") Z3 encodings, and everything is checked mechanically.
- The models under evaluation are qwen2.5-coder 7B and llama3.2 3B now, with Gemini 2.5 Flash / Flash-Lite later.

**The library, in plain words**

| Module | What it does |
|---|---|
| `dataset.py` | Loads instances. Checks whether an input satisfies the preconditions. Cleans up witnesses (e.g. turns `"INT_MIN"` into a number). Holds the safety specification shown to the models. |
| `cexec.py` | Compiles each C function with the sanitizers into a small driver program. Runs inputs through it and reports which violation (if any) happened. **This is the ground-truth oracle.** |
| `z3_child.py`, `z3run.py` | Runs model-written Z3 scripts in a **sandbox**: separate process, no API keys in its environment, no network, no file writes outside a temp folder, time and memory limits. Reads the counterexample out of the solver's model, then **re-runs it on the real C code** to confirm or refute it. |
| `prompts.py` | Every prompt used, in one place. The report quotes from it. |
| `llm.py` | Clients for Ollama (local) and Gemini (API). Every response is cached in SQLite, so runs can be resumed and reproduced exactly. |
| `parse.py` | Pulls the verdict JSON and the Python code out of free-form model replies. Tolerant of messy output. |
| `approaches.py` | The five approaches, including the repair loop. |
| `fuzz.py`, `cbmc.py` | Two classic non-AI tools: random testing, and the CBMC bounded model checker (Clarke et al. 2004, in our references). |
| `analysis.py` | Metrics, confidence intervals, McNemar tests, the Z3 failure taxonomy, and hybrid policies. |

## 4. The dataset

### 4.1 Design

| Tier | What it tests | Pairs | Example |
|---|---|---|---|
| T1 | straight-line arithmetic (the proposal's fallback) | 20 | `return (lo + hi) / 2;` overflows when both are large |
| T2 | branches, guards, early returns, dead code | 19 | an overflow check `if (a + b < a)` that itself overflows |
| T3 | loops | 13 | `for (unsigned i = n - 1; i >= 0; i--)` never terminates normally and reads `a[UINT_MAX]` |
| T4 | helper functions, nested loops | 8 | a `safe_div` helper returns 0 and the caller then divides by that 0 |

Bug classes over the 120 instances: bounds 38, overflow 36, div_zero 26, shift 20. Exactly half are UNSAFE in every tier and class, so chance accuracy is 50%.

**Minimal pairs.** Every UNSAFE function has a SAFE "twin":
- **Code twins (37 pairs):** the bug is fixed in one or two lines, e.g. `lo + (hi - lo) / 2`.
- **Precondition twins (23 pairs):** identical code, but the caller guarantees something stronger. For example, `area(w, h) = w * h` is unsafe for sides up to 50000 and safe for sides up to 46340, because 46340² still fits in an int.

Precondition twins catch models that pattern-match ("this looks like a bug") instead of reasoning. Such a model must get one of the two twins wrong. We therefore report **pair accuracy** (both twins right) next to plain accuracy.

**Deliberate traps** where intuition and C semantics disagree:
- In C, `-7 % 2` is `-1`, but Z3's bit-vector `%` gives `1`.
- `INT_MIN / -1` overflows.
- `1 << 31` is undefined for a signed int.
- Unsigned wraparound is legal, but `UINT_MAX + 1` used as a divisor is 0.
- One decoy: a branch whose condition `k > 5 && k < 3` can never be true.

### 4.2 How each label is checked

Every label is checked four independent ways (`scripts/validate_dataset.py`):

1. **Executed witness (UNSAFE):** a hand-written input must satisfy the preconditions and must crash the sanitized C program.
2. **Reference Z3 encoding:** must give the right verdict. For UNSAFE, its counterexample is re-executed and must crash too.
3. **CBMC** (an industrial bounded model checker) must agree.
4. **Fuzzing (SAFE):** 3,000 random inputs that respect the preconditions must produce no crash.

All 120 labels passed. The final re-run on the frozen dataset passed 120/120 (`dataset/VALIDATION.md`).

### 4.3 Two interesting engineering notes (useful for the report)

- **Nonlinear arithmetic is hard for solvers.** Proving that `sum of a[i]*a[i]` cannot overflow timed out in Z3. The reference encodings fix this with a *lemma*: a separate solver first proves a one-variable fact about the square, and the main formula then uses that fact. One loop (Euclid's GCD) is proved safe with an *inductive invariant* instead of unrolling. Both are good examples for the "solver limitations" discussion.

### 4.4 The excluded stress pair

The classic "is it safe to multiply?" check (`b <= INT_MAX / a`) defeats both Z3 and CBMC: they time out on 32-bit multiplication combined with division. We know its label by reasoning, but no tool can confirm it, so it is excluded from scoring and kept as a **case study**. Even a perfect translation into Z3 can fail because the solver gives up, not because the LLM made a mistake.

## 5. How answers are scored

- **Verdict accuracy.** Each answer is SAFE, UNSAFE or UNKNOWN (no usable answer, or the Z3 script crashed). UNKNOWN counts as wrong.
- **Witness confirmation.** Whenever any system says UNSAFE and gives a concrete input (direct answers are asked for one; Z3 gives one automatically), we **run that input on the real C code**. A bug report is then either *confirmed* (the sanitizer fires) or *not reproduced*. This is the project's main methodological contribution: the tool approach can check its own bug reports, while a "SAFE" answer can never be checked this way.
- **Z3 failure taxonomy.** Each model-written script is classified:
  - proved safe;
  - bug found and confirmed;
  - spurious counterexample (false alarm);
  - missed bug;
  - or the error type: hallucinated function, type misuse, Z3 API misuse, syntax, timeout, and so on.
- **Statistics.**
  - Wilson 95% confidence intervals.
  - Exact McNemar tests, paired by instance, with Holm correction.
  - Breakdowns by tier, bug class and twin type.
- **Derived policies (no extra model calls).**
  - "Use Z3, fall back to CoT if the script failed".
  - "Only report bugs whose witness reproduces".

## 6. Approaches and models

| Approach | One-line description |
|---|---|
| `direct` | "Answer immediately with only JSON: verdict, violation type, witness." |
| `direct_cot` | "Think step by step about every array access, division, arithmetic op and shift; then give the JSON." |
| `z3` | "Write a Z3 script: declare the parameters, create solver `s`, add preconditions, add one 'some violation happens' constraint." |
| `z3_guided` | Same, plus a cheat-sheet (use 32-bit bit-vectors, C `%` is `SRem`, the exact names of Z3's overflow helpers, how to unroll loops) and one worked example. |
| `z3_repair` | Same as guided, plus up to 3 feedback rounds. The model sees its script's error (with a "did you mean …?" hint for made-up function names) or is told that its counterexample did not reproduce on the real code. It is **never told the correct answer.** |

Models:
- `qwen2.5-coder:7b` and `llama3.2:3b` run locally via Ollama, at temperature 0.
- Gemini 2.5 Flash-Lite and Flash are configured and need a key. Their "thinking" is switched off so that `direct` really is direct; switching it on is a ready-made ablation.

Non-AI baselines: gold Z3 (Claude's encodings: what a perfect translator would get), CBMC, dictionary fuzzing and random fuzzing.

## 7. Results so far

**Final (non-AI baselines, 120 instances):**

| System | Accuracy | Notes |
|---|---|---|
| Gold Z3 (Claude-written encodings) | 100% | Upper bound for the translation approach: if the LLM translated perfectly, this is what it would get. Average 0.5 s per instance. |
| CBMC | 100% | The classical tool; needs no translation at all. Average 1.7 s per instance. |
| Dictionary fuzzing (1,000 inputs) | 98.3% | Misses 2 bugs that need very specific large inputs. |
| Random fuzzing (1,000 inputs) | 85.0% | Misses 18 bugs. It can never prove anything SAFE; it just doesn't find a crash. |

**Preliminary (LLMs, incomplete):**

| Model | Approach | Done | Accuracy | Bugs caught (recall) | Safe correctly passed |
|---|---|---|---|---|---|
| qwen2.5-coder 7B | direct | 120/120 | 55.8% | 25% | 87% |
| qwen2.5-coder 7B | direct + CoT | 42/120 | ~55% | ~14% | ~95% |
| llama3.2 3B | direct | 79/120 | ~56% | ~13% | ~98% |

**Early observations:**
1. **The small models are heavily biased towards "SAFE".** They pass almost everything, so their accuracy sits near 50% while they miss most real bugs. For a code-review assistant this is the dangerous failure mode: false assurance. It feeds straight into the Responsible AI discussion.
2. **Smoke test of the Z3 approach (qwen, 2 pairs).**
   - The model **invented Z3 functions** that don't exist (`BVModNoOverflow`, `BVSDivNoUnderflow`).
   - It made Python operator-precedence mistakes (`h < 0 | h >= size`).
   - It claimed `INT_MIN / -1` is representable.
   - Without the hint added later, it resubmitted the same broken script in every repair round.
   
   These are exactly the proposal's "knowledge required by the tool is not easily obtained by the LLM" failure modes, now with concrete examples.

## 8. Quality control: issues found and fixed

Two review agents audited the code and the drafted report:

| Issue | Effect | Fixed by |
|---|---|---|
| Witness values like `"zero"`, or a missing parameter, silently became 0 and could be "confirmed" | inflated confirmation rates | strict parsing, plus support for `"INT_MAX - 1"` |
| `INT_MIN` inside the explanation text broke JSON parsing | lost witnesses | string-aware lenient parsing |
| The guidance said Z3 integer division "rounds toward −∞"; it is actually Euclidean | small inaccuracy in a prompt | corrected **before** any guided run used it |
| The validation script's time limit was capped below what it requested | one false validation failure | limits are now forwarded correctly |
| Compile race, F1 edge case, Windows line endings | latent | fixed |

The qwen run started before these fixes. Because every raw reply is stored, `scripts/rescore.py` re-scores all records with the fixed code once the runs finish, so every answer is judged by the same code. Tests: **144 passing**.
